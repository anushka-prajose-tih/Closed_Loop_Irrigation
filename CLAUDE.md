# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Sambhav is STM32G0B1RETX firmware for a battery-powered, RTC-scheduled environmental and soil monitoring node. Each wake cycle it polls I2C/Modbus/ADC sensors, logs a binary record to external SPI flash, updates an OLED display, and periodically publishes a JSON payload over MQTT through an always-on GSM modem, which also listens for motor/command/OTA messages. See [README.md](README.md) for the sensor list, peripheral map, and block/flow diagrams.

The README describes the current implementation (SMKB weather station, MQTT upload, no standby) at overview level, with per-function flow diagrams. This file is the source of truth for the byte-level record format, the Modbus map, and the constraints on changing them; update the README's diagrams alongside any change to the control flow.

**Superseded code is commented out in place, not deleted** (the old weather block in `Read_data()`, its decode in `read_flash_create_json()`, the old query arrays, the old `flash_data_size`). Leave those blocks alone unless asked — they are the rollback path. Don't "clean them up" as drive-by tidying.

## Build

This is an STM32CubeIDE (Eclipse CDT managed-build) project, not a Makefile/CMake project.

- **Build**: open the project in STM32CubeIDE and build the `Debug` or `Release` configuration, or use the headless builder:
  `stm32cubeide.exe --launcher.suppressErrors -nosplash -application org.eclipse.cdt.managedbuilder.core.headlessbuild -data <workspace> -build Sambhav_V3/Debug`
- **Fast compile check**: CubeIDE generates `Debug/makefile` (gitignored, regenerated by the IDE — never hand-edit it or the `subdir.mk` files). If `make` and the GNU ARM toolchain are on PATH, `make -C Debug all` recompiles without launching the IDE. Neither is on PATH by default on this machine; add CubeIDE's bundled `tools/bin` and `arm-none-eabi` directories first.
- **Toolchain**: GNU ARM GCC (`arm-none-eabi-`), target MCU `STM32G0B1xx`, board reference `NUCLEO-G0B1RE`. Global define: `USE_HAL_DRIVER`.
- **Linker scripts**: [STM32G0B1RETX_FLASH.ld](STM32G0B1RETX_FLASH.ld) (default) and [STM32G0B1RETX_RAM.ld](STM32G0B1RETX_RAM.ld).
- **Flash/debug**: via ST-Link using the `Sambhav_V3 Debug.launch` configuration, or STM32CubeProgrammer.
- There are no unit tests, linter, or CI config in this repo — validation is done by building in CubeIDE and testing on real hardware (or a NUCLEO-G0B1RE dev board).
- [Sambhav_V3.ioc](Sambhav_V3.ioc) is the CubeMX peripheral configuration file. If you change pin/peripheral config, regenerate code from the `.ioc` in CubeMX/CubeIDE rather than hand-editing the `MX_*_Init()` functions in [main.c](Core/Src/main.c) — CubeMX will overwrite anything outside `USER CODE BEGIN/END` blocks on regeneration.

## Debugging on hardware

There is no semihosting or SWO. The only runtime log channel is `serial_print()` / `serial_print_inline()` in [main.c:757](Core/Src/main.c#L757), which writes to **USART6 at 115200 8N1**. Attach a USB-serial adapter there to trace a cycle — every stage (`BOOTUP`/`WAKEUP` banners, device ID, per-sensor values, flash addresses, the full outgoing JSON, next alarm time) is printed. `printf()` is called in a couple of places in [w25q32jv.c](Core/Src/w25q32jv.c) but is not retargeted, so that output goes nowhere.

## Architecture

All application logic lives in [Core/Src](Core/Src) and [Core/Inc](Core/Inc); [Drivers/](Drivers) is unmodified ST HAL/CMSIS code.

**[main.c](Core/Src/main.c)** is the whole application, not just HAL init boilerplate. Key entry points:

- `main()` — after peripheral/driver init it sets `bootup_flag` and spins in `while(1)`, calling `App_operation()` whenever `bootup_flag` or `RTC_alarm_flag` is set, calling `MQTT_app_poll()` on every pass in between, and diverting into blocking menu mode when `Rotary_button_pressed` is set.
- `App_operation()` ([main.c:873](Core/Src/main.c#L873)) — the per-cycle orchestrator: probes the flash device ID (expects `0x16`) and loads the address map, on the first cycle powers the modem (only if it doesn't already answer `AT`), syncs time and connects MQTT, then calls `Read_data()`, `Oled_Data_display()`, `GSM_post_sequence()`, then `rtc_set_alarm()`.
- `Read_data()` ([main.c:926](Core/Src/main.c#L926)) — polls every sensor (I2C SCD41/SHT45, Modbus RTU NPK/pH/leaf-wetness/soil/weather/PAR, ADC battery/solar) and packs the results into `backup_array`, then writes that record to flash.
- `GSM_post_sequence()` ([main.c:1522](Core/Src/main.c#L1522)) — at the scheduled post hour (or on boot), drains flash from `flash_read_address` up to `flash_write_address`, rebuilding one JSON payload per record via `read_flash_create_json()` and publishing each on the MQTT `data` topic (QoS 1). `flash_read_address` only advances on a successful publish, so unsent records survive a reset. Gives up after 5 consecutive failures, and skips the drain entirely while `mqtt_connected` is 0. The old HTTP POST call is commented out beside it.
- `MQTT_app_poll()` ([main.c:1744](Core/Src/main.c#L1744)) and its helpers at the end of `USER CODE 4` — the device behaviour from the backend's `device_simulator.py`, described under GSM/MQTT below.
- Globals declared in the `USER CODE BEGIN PV`/`PFP`/`4` blocks (sensor values, flags like `bootup_flag`/`RTC_alarm_flag`/`flash_ready_flag`, the Modbus query byte arrays) are the shared state threaded through these functions — there's no app struct.
- `check_wakeup()` exists and is declared in [main.h:69](Core/Inc/main.h#L69) but is **never called** — it is leftover standby-resume handling. Don't assume it runs.

### The 70-byte record format is the central contract

The flash record is a flat binary blob, `flash_data_size` = **70 bytes**: `0xAA` header, 4-byte big-endian UNIX timestamp, then fixed-offset big-endian sensor fields, then a `0xEE` trailer at index 69. Nothing describes this layout except the code, and it is **written and read in two different files**:

- **Writer**: `Read_data()` in [main.c](Core/Src/main.c#L926) appends raw bytes straight off the wire into `backup_array` via `backup_array_size++`.
- **Reader**: `read_flash_create_json()` in [w25q32jv.c](Core/Src/w25q32jv.c) walks the same bytes with a running `index` through `convert_to_16bit_data()` / `convert_to_32bit_data()` / `convert_to_float_data()`, and emits the server JSON.

Current layout (offset, width, field — every multi-byte field is big-endian):

| Off | W | Field | Off | W | Field |
|---|---|---|---|---|---|
| 0 | 1 | `0xAA` | 41 | 2 | solar radiation, W/m² (int16) |
| 1 | 4 | UNIX timestamp (GMT) | 43 | 2 | weather air temp ÷10 |
| 5 | 2 | CO2 raw (SCD41) | 45 | 2 | weather air RH ÷10 |
| 7 | 4 | SHT45 temp raw, RH raw | 47 | 2 | pressure ÷10 |
| 11 | 6 | N1, P1, K1 | 49 | 2 | rain intensity ×0.03 |
| 17 | 6 | N2, P2, K2 | 51 | 2 | accumulated rain ÷10 |
| 23 | 2 | pH ÷100 | 53 | 2 | wind speed ÷100 |
| 25 | 2 | leaf wetness 1 ÷10 | 55 | 2 | wind direction (vane) |
| 27 | 2 | leaf wetness 2 ÷10 | 57 | 2 | wind direction (ultrasonic) |
| 29 | 6 | SM1 ÷100, ST1 ÷100, EC1 | 59 | 2 | PAR ×3.33 |
| 35 | 6 | SM2 ÷100, ST2 ÷100, EC2 | 61 | 8 | battery ADC, solar ADC (u32 each) |
| | | | 69 | 1 | `0xEE` |

Consequences to respect when touching sensor data:

- **Scaling is applied on readback, not on write.** Raw sensor counts go into flash; every divisor/factor in the table above, plus the ADC→battery-volts and ADC→solar-radiation formulas, lives in `read_flash_create_json()`. Changing a calibration constant means editing the reader, not `Read_data()`. The values shown on the OLED are computed separately in `Read_data()`/`Oled_Data_display()`, so a calibration change must be mirrored there or display and server will disagree.
- **The weather-station registers are signed with a `0x7FFF` "no reading" sentinel.** `Read_data()` stores the raw bytes *before* clamping, so the clamp exists in **both** files and must stay in both. Decode through `(int16_t)` — `convert_to_16bit_data()` returns `uint16_t`, so a missing cast turns sub-zero temperatures into ~6553 °C.
- **Adding, removing, or resizing a field requires four coordinated edits**: the packing in `Read_data()`, the `flash_data_size` constant at [main.c:66](Core/Src/main.c#L66), the decode sequence in `read_flash_create_json()`, and the `sprintf` JSON format string + argument list at the end of that function. Miss one and every field after the change point silently decodes as garbage.
- `flash_write_address` advances by the *actual* `backup_array_size`, but `flash_read_address` advances by the *constant* `flash_data_size`. If `Read_data()` ever packs a different number of bytes, the reader desynchronizes from the writer permanently. To check the writer after an edit, total every live advance of `backup_array_size` in `Read_data()` — both the `backup_array_size++` writes and the bulk `backup_array_size += N` after the NPK/soil/ADC copy loops — ignoring commented-out blocks, and confirm the decoder's running `index` lands exactly on the trailer.
- **A record can never exceed 100 bytes.** `backup_array` is a global `[100]` with no bounds checks, and the write-time read-back buffer in `Read_data()` is sized `sizeof(backup_array)` so it tracks it automatically. Going past 100 means enlarging `backup_array` itself. The read-back is deliberate, not dead code: `read_flash()` echoes the bytes to USART6, which is the only on-log confirmation that a write reached the chip.
- **Changing the record size invalidates everything already in flash.** Old records fail the `0xEE` trailer check at the new offset and post as zeros; erase the log when deploying a layout change.
- The JSON schema is wider than the sensor set — unpopulated keys (`Tc2`, `O2c`, `UV`, `LAI`, `pH2`, …) are hardcoded to `0`. Some keys are also repurposed rather than literal: `NDVI` carries rain intensity, and the weather object's `SR` carries the dedicated solar sensor. The payload buffer is an 800-byte stack array in `GSM_post_sequence()`.

### Flash log as a ring buffer

[w25q32jv.c](Core/Src/w25q32jv.c)/[.h](Core/Inc/w25q32jv.h): records are appended from address 0 up to `WRITE_ADDRESS_LOCATION` (0x3FF000), then wrap. An address-map region at `WRITE_ADDRESS_LOCATION`/`READ_ADDRESS_LOCATION`/`ERASE_ADDRESS_LOCATION` (plus stored `time_interval`/`GSM_interval`) persists the three pointers across reboots via `write_address_map()`/`read_address_map()`, so unposted data and the configured intervals survive a power cycle.

- **Records never straddle a 256-byte page.** `flash_next_write_address`/`flash_next_read_address` track the next page boundary; when fewer than `flash_data_size` bytes remain in the current page the pointer jumps to the next page and the tail is wasted. Writer and reader each implement this skip independently — they must stay in agreement or the reader lands mid-record.
- `read_flash()` sends its clock bytes from a 1-byte `dummy` global but passes the full read length to `HAL_SPI_TransmitReceive`, so every multi-byte read (including the 70-byte record reads during GSM posting) reads past the end of `dummy`. It's harmless in practice: it only reads, never writes, and the chip ignores MOSI during a fast read. It is still a known out-of-bounds access, and it hasn't been fixed.
- `write_node_data()` erases the 4 KB sector automatically whenever the target address is sector-aligned (`address % 0x1000 == 0`).
- `flash_write_address` and `flash_read_address` advance independently; the writer must never lap the unsent reader. If `flash_read_address > flash_write_address` after a post pass, `GSM_post_sequence()` treats the log as corrupt and resets both pointers to 0.

### Other subsystems

- **GSM/MQTT** ([GSM_EC200U.c](Core/Src/GSM_EC200U.c)/[.h](Core/Inc/GSM_EC200U.h)): AT-command driver for the Quectel EC200U over USART4 (115200), driven by UART TX/RX-complete interrupt callbacks in `main.c` (`HAL_UART_TxCpltCallback`/`RxCpltCallback` forward to `GSM_UART_*CpltCallback`). Replies land byte-by-byte in the global `aRxBuffer[1024]`. Broker, APN, topics and the TTI unit are compile-time constants in `GSM_EC200U.h`. The active upload path is plain MQTT to `MQTT_HOST`:`MQTT_PORT` (currently `test.mosquitto.org:1883`, no auth); the HTTP upload (`GSM_HTTP_sendDataToServer`, its prototype and `SERVER_URL`) is commented out in place as the rollback path. `GSM_httpGet()` is still live because `GSM_time_sync()` falls back to it when `AT+QLTS` fails. The older one-shot `GSM_MQTT_sendDataToServer` and its SSL variant are still compiled but unused.
  - **The MQTT contract is set by an external Python backend, not by this repo**: `device_simulator.py` / `onem2m_bridge.py` (bridge to a oneM2M Mobius CSE). The firmware publishes on `data` (the flash-record JSON, QoS 1) and `motor_status` (`{"timestamp","Device_ID","status":"on"|"off"}`, QoS 1, **retained**), and subscribes to `motor_cmd` (`cmd` `start`+`tti` / `stop`), `cmd` (logged; `reset` stops the motor, it does **not** reset the MCU) and `ota` (logged only, no update happens). Incoming messages whose `Device_ID` isn't `SAMBHAV_<uid>` are ignored. The MQTT client ID is that same `Device_ID`. Change topics or payload shapes only in step with the backend.
  - **There is no motor hardware.** "Motor" is a software timer (`tti` × `MQTT_TTI_UNIT_SECONDS`, clamped 0–255) checked in `MQTT_app_poll()`; no GPIO is driven. A real relay pin must be added through the `.ioc`.
  - **Incoming messages use the modem's buffer mode** (`AT+QMTCFG="recv/mode",0,1,0`): the modem queues up to 5 messages and emits only `+QMTRECV: 0,<id>`. `MQTT_app_poll()` spots that URC (or `+QMTSTAT:`, link dropped) by scanning `aRxBuffer` with no AT traffic, else falls back to an `AT+QMTRECV?` poll / `AT+QMTCONN?` link check every 30 s, then clears the buffer so only fresh URCs count. Nothing is polled while `App_operation()` or the rotary menu is running, so a motor stop can be late by a full cycle, and never happens at all once the menu is entered.
  - **Two parsing styles coexist in the driver.** The older functions send, then call `GSM_resetRxBuff()` and check fixed byte offsets (e.g. `aRxBuffer + 12`); the MQTT functions (`_sendCommand`/`_waitForLine`) clear the buffer *before* sending and search for tokens. A URC arriving mid-command can shift the fixed offsets and make an old-style check (notably `GSM_networkCheck()`) fail spuriously. Use the token style for new code.
  - `aRxBuffer` is 1024 bytes because the modem echoes an entire ~800-byte publish payload before the `+QMTPUBEX` result; shrinking it loses publish confirmations. Copy it into `print_char[200]` only with `snprintf`.
- **RTC scheduling** ([rtc_sync.c](Core/Src/rtc_sync.c)/[.h](Core/Inc/rtc_sync.h)): computes the next wake alarm from `time_interval` and the next GSM post hour from `GSM_interval` (`GSM_POST_time`). `HAL_RTC_AlarmAEventCallback` in `main.c` just sets `RTC_alarm_flag`; all the real scheduling math is here.
- **Modbus RTU** ([modbus_rtu.c](Core/Src/modbus_rtu.c)/[.h](Core/Inc/modbus_rtu.h)): request/response framing and CRC over USART3/RS485 at 9600 8N1 for all the external soil/weather/NPK/pH sensors. Query byte arrays (slave address + function code + register range, with CRC filled in by `Add_CRC()` — any CRC bytes written into the literal are overwritten) live as globals near the top of `main.c`. Response byte layout is decoded inline in `Read_data()`, so changing a sensor's register map means updating both the query bytes and the corresponding offsets in `Read_data()`.
  - Live slave map: `0x01` NPK1, `0x02` soil 1, `0x03` solar radiation, `0x04` leaf wetness 1, `0x05` SMKB weather station, `0x06` soil 2, `0x07` NPK2, `0x08` leaf wetness 2, `0x0A` PAR, `0x0B` pH. Every address must stay unique: `get_modbus_data()` validates only that byte 0 echoes the requested address, so two devices sharing one would be indistinguishable.
  - `get_modbus_data()` is fully blocking: 500 ms settle, transmit, up to 4 s receive, 500 ms settle, one retry. **A failed read is indistinguishable from a zero reading** — the buffer is left memset to zero and packed into the record with no error flag and nothing on the serial log.
  - **`modbus_RX` must be at least as large as the biggest response in use.** It is sized `[40]` in `Read_data()` because the 14-register weather read returns 33 bytes; `HAL_UART_Receive` writes the requested length with no bounds check, straight into neighbouring stack variables. Check this whenever a register count grows.
  - `write_modbus_register()` issues a single FC06 (write single register) and only logs OK/FAILED to serial; nothing checks the result. Its one caller is the daily weather-station reset in `App_operation()` (see Timing).
  - `setMidLitEnd()` (mid-little-endian word swap for IEEE-754 float registers) is still exported by `modbus_rtu.c` but is **dead** — its only callers are inside the commented-out old weather block. The live sensors all use scaled 16-bit integers.
- **I2C sensor conversions** ([i2c.c](Core/Src/i2c.c)/[.h](Core/Inc/i2c.h)): raw-word→engineering conversions and CRC-checked buffer extraction for the SCD40/SCD41 and SHT sensors. Despite `SHT21`/`SHT85` variants still present in this file and lingering "SHT85" buffer names in `main.c`, the live path is `Get_SHT45_values()` + `calc_temp_SHT45()`/`calc_humid_SHT45()`. The bus transactions themselves are issued inline against `hi2c3` in `Read_data()`; SHT45 acquisition takes 5 samples and uses the median for stability.
- **Display** ([ssd1306.c](Core/Src/ssd1306.c)/[.h](Core/Inc/ssd1306.h), [fonts.c](Core/Src/fonts.c)): SSD1306 OLED driver over I2C2. `main.c`'s `printDisplay()`/`printDisplay_level()` wrap it for status/error/menu text.
- **User interface** ([rotary_encoder.c](Core/Src/rotary_encoder.c)/[.h](Core/Inc/rotary_encoder.h)): TIM1 encoder-mode quadrature decoding plus button EXTI handling. A long press (>3s, detected in `HAL_GPIO_EXTI_Falling_Callback` in `main.c`) sets `Rotary_button_pressed`, which diverts `main()`'s loop into a blocking menu mode (`ROT_ENC_handler()`/`printHandler()`) for configuring `time_interval` and `GSM_interval`, persisted via `write_address_map()`.

## Timing and power behaviour — read before changing scheduling

- **The GSM modem is never powered down.** It stays on and connected for MQTT; the `GSM_power_up()`/`GSM_power_down()` calls in `GSM_post_sequence()` are commented out. After an MCU reset the modem is usually still running, and a PWRKEY pulse would switch it *off*, so boot calls `GSM_power_up()` only when `GSM_isAlive()` gets no `AT` reply. `MQTT_app_connect()` always sends `QMTDISC`/`QMTCLOSE` first to drop any session left from before the reset.
- **The node does not currently enter standby.** `HAL_PWR_EnterSTANDBYMode()` at the end of `rtc_set_alarm()` ([rtc_sync.c:149](Core/Src/rtc_sync.c#L149)) is commented out, so the MCU stays in `while(1)` between cycles and is woken by the alarm *interrupt* setting `RTC_alarm_flag`. Re-enabling it changes the control flow substantially: every wake becomes a full reset, `RTC_alarm_flag` is never seen set, and `bootup_flag` is 1 on every cycle — which would make `GSM_post_sequence()` post unconditionally instead of only at the scheduled hour. Power/GPIO cut lines (`I2C_Cut_Pin`, `RS485_Cut_Pin`, `FLASH_CS_Pin`, `GSM_KEY_Pin`) gate power to peripheral buses as part of that low-power design — check these before assuming an I2C/RS485 device is always powered.
- **The RTC runs in GMT.** `GSM_post_sequence()` adds a hardcoded `19800` seconds (IST, UTC+5:30) before deciding whether the current hour matches the post schedule, but the timestamp written into the record and into the JSON is the unshifted GMT value.
- `App_operation()` does a scheduled daily restart at **03:15 GMT** (08:45 IST), only on a non-boot cycle (`bootup_flag == 0`), and only if a wake actually lands on that minute. Just before `HAL_NVIC_SystemReset()` it writes `0x0000` to register `0x00F2` on the SMKB weather station (slave `0x05`) to clear its errors.
- A cycle is slow by construction and `Read_data()` blocks throughout: each of the 10 Modbus reads costs at least 1 s of settle delay (up to ~9 s on a timeout + retry), there is a debug `HAL_Delay(5000)` after the weather block, and `Oled_Data_display()` walks 30 screens at `DISPLAY_DELAY` (800 ms) ≈ 24 s. Don't add work to this path assuming it is cheap, and don't mistake the delays for jitter that needs fixing without checking why they are there. The old weather station's daily `>RESET` at 08:30 IST was replaced by the register-`0x00F2` write described above.
- Sensors are only read once the RTC year is ≥ 2024 (`time_tm.tm_year - 100 >= 24`); before time sync succeeds the cycle silently skips straight to setting the next alarm and logs nothing.
- Configurable via the rotary menu and persisted in flash: `time_interval` (5/10/15/30/60 min, default 15) and `GSM_interval` (1/2/3/4/6/12/24 h, default 1).
